# IER 技术路线（实施版）

## 1. 任务定义

给定用户历史交互序列 `H_u` 与候选物品 `i` 的证据集合 `E_i={e_1,...,e_m}`，预测下一次交互或 Top-K 偏好。每个证据单元保留来源与位置：商品图 URL/本地路径、评论 ID 与文本、描述字段或属性键值。

模型不把“出现次数”直接解释成重要性。用户历史产生多个兴趣原型 `h_1,...,h_K`；每个兴趣原型在候选证据中动态取 Top-k，随后进行密度/近重复校正和跨兴趣聚合。

## 2. 最小可复现模型

```text
用户历史物品/UGC -> 多兴趣编码器 -> h_1 ... h_K
候选图片/评论/属性 -> 证据编码器 -> e_1 ... e_m
(h_k, e_j) -> 兴趣条件相关性 -> Top-k evidence
证据相似图/密度 -> 重复惩罚 -> 鲁棒聚合
协同过滤主干分数 + 证据分数 -> 最终排序
```

第一版不做昂贵的端到端视觉微调：冻结文本/视觉编码器并缓存单条证据向量，只训练推荐主干、兴趣原型与聚合器。这样能将性能变化明确归因到证据选择与聚合，而不是大模型容量。

## 3. 训练目标

`L = L_rec + lambda_red * L_red + lambda_sens * L_sens`

- `L_rec`：BPR 或 sampled-softmax 的推荐损失。
- `L_red`：复制同一或近重复证据前后，用户—物品分数与排序应保持稳定。
- `L_sens`：移除与某兴趣最相关的关键证据后，该兴趣通道的证据分数应按 margin 合理下降；不能用总分盲目下降替代兴趣通道监督。

重要边界：`L_sens` 只在“关键证据”可由相关性或人工诊断确认的样本上使用，否则会把随机缺失误当成语义缺失。

## 4. 对照与消融

- 非个性化：MostPop。
- 纯协同：BPR-MF、LightGCN；序列版加入 SASRec。
- 简单内容：ContentMean / VisualMean、VBPR。
- 多模态图模型：MMGCN、GRCN、LATTICE、BM3、FREEDOM（统一由 MMRec 运行，首轮选 2–3 个）。
- IER 消融：无多兴趣、无动态取证、无重复惩罚、无 `L_red`、无 `L_sens`、全局均值池化。

## 5. 评测协议

- CleanRec：Recall@10/20、NDCG@10/20、MRR。
- DuplicateBench：同一证据复制 1/2/4/8 次；报告 score drift、rank drift、Top-K overlap。
- NoiseBench：从不相似物品注入 1/2/4/8 条证据；报告相对性能下降。
- MissingBench：分别移除随机证据、最高相关证据、某一模态；区分“合理敏感”与“脆弱”。
- SparseBench：按冷用户、冷物品和短序列分桶。

所有干预只作用于验证/测试候选内容，默认不改变正负交互标签。报告相同候选集、随机种子和负采样集合下的配对差异。

## 6. 数据路线

通用主线已确定为 Amazon Reviews 2023 `Musical_Instruments` 官方 5-core；`All_Beauty` 的官方 5-core 只有 2,535 条交互，因此降级为代码 pilot，不进入论文主表。正式数据保留每条评论文本/评论图、商品多图、描述和属性；目标时刻只允许使用严格早于目标且非目标用户撰写的评论证据。

正式验证/测试共生成 114,710 个 warm 目标，`robustness/targets.parquet` 为每个目标固定随机锚证据、异商品噪声证据与稀疏分桶。Duplicate 的额外复制数和 Noise 的注入数均为 1/2/4/8；模型相关的“关键证据移除”必须在取得兴趣条件相关性后在线构造。

旅游阶段再审计 MMPOI 的 NYC/TKY 原始数据，检查其所谓多模态内容是否保留逐条图片/评论，还是仅有每 POI 的全局特征。只有前者才能作为 IER 的主旅游实验；否则 MMPOI 只做推荐准确率与迁移基线，Flickr/YFCC 承担逐条 UGC 证据实验。
